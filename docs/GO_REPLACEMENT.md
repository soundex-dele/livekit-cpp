# Go LiveKit 主服务完整替代

更新：2026-10-27，Asia/Shanghai。状态：实施中，尚未完成替代。

## 范围与基线

用户已确认：用 C++ 替换 LiveKit 主服务，继续兼容现有 Egress、Ingress、SIP 和
Agent worker；不要求重写这些独立服务。生产主服务不能启动、代理到或嵌入 Go
LiveKit 来补功能。测试允许启动 Go 参考服务作行为对照。

- Go 参考：`D:/workspace/livekit`，`a390d03d28c895742d9b13c0894880ee67733801`，
  `version.Version = 1.13.10`。
- 协议：`f09f87aab29b865850a967924726bf76b7db4755`。
- 实现位置：本平台 `livekit-cpp` 子模块，起点 `a21f3c0`；同级旧仓库保留不覆盖。
- 媒体底层继续复用 libwebrtc，应用负责协商映射、路由、权限、选层及调度。
- 对照对象是固定提交中的开源服务实际行为。协议 schema、客户端方法及云产品文档
  不单独构成支持证据。升级 Go 基线必须重新生成差异和验收报告。

现有 `IMPLEMENTATION.md` 包含更广的平台产品规划。本计划限定主服务替代，不把
移动端 SDK、管理后台或自行重写录制/混流 worker 列作替代主服务的前置条件。

## 完成定义

“完整替代”必须同时满足以下条件，不能用已实现 API 数量或单个 Demo 通过代替：

1. 官方客户端及服务端 SDK 在声明的平台和版本上无需业务代码改造即可接入。
   `/rtc`、`/rtc/v1`、Twirp JSON/protobuf 的请求、响应、权限、事件与错误语义一致。
2. 对基线实际支持的编码、分层、数据及恢复路径有端到端行为证据；协议可解析、
   libwebrtc 内部存在算法、服务进程健康均不等于对应功能已交付。
3. 兼容 Go 的部署入口和有效配置语义，包括 YAML、环境变量/CLI、网络候选、
   Redis、TURN、限制、日志及监控。未实现的非默认配置不得静默忽略。
4. 多节点路由、会话恢复、drain 与故障处理经过验证。不得承诺基线并不保证的
   节点宕机后无缝媒体迁移；按基线区分信令恢复、ICE restart 和完整重连。
5. 独立 Egress、Ingress、SIP、Agent worker 与 C++ 主服务实际联调通过。
   Twirp 外壳只是入口，还须实现 Redis/PSRPC 通信、状态存储、回调与生命周期。
6. 修复既有回归；完成弱网、延迟、容量及稳定性门槛，同机同负载对照 Go。
   测试报告保存源码版本、配置、二进制哈希和失败记录。
7. 灰度部署、回滚及升级流程有演练记录。未满足全部门槛前保留 Go 的生产入口。

## 实施依赖与顺序

1. **R00/R01：可重复的兼容门禁。** 先从无媒体房间 API 开始，再扩展参与者、
   双协议和真实媒体。每个修复保留修复前失败及修复后结果，不修改基线迁就 C++。
2. **R02/R03 + 现有媒体回归：连接和授权正确性。** 关闭四轨帧数、跨系统 LOW
   超时与 401，验证信令生命周期，再扩展协议。权限与恢复不可留到上线前补。
3. **R04–R08：媒体和网络兼容。** 每个编码/分层路径独立验收；E2EE 需要调整
   当前依赖 VP8 完整组帧的路径，不能仅删除加密拒绝条件。
4. **R09/R10/R11：部署与集群基础。** Redis/PSRPC 是连接现有外部服务的核心依赖；
   先验证线协议、请求生命周期、节点/房间状态，再接业务服务。
5. **R12–R14：真实外部服务联调。** API 权限、worker 执行、状态回传和 Webhook
   形成完整链路；替代主进程时不替换外部 worker。
6. **R15：替代发布。** 全量门禁后进行可回滚灰度；未做设备人工验收的组合继续
   标明未验收，自动化截图/合成媒体不能代替真机结论。

## 验收门槛

保留既有目标：正常网络入房成功率 ≥99.5%，远端首帧 P95 ≤2 s，采集到播放
P95 ≤300 ms，连通恢复后媒体恢复 P95 ≤10 s；10% 随机丢包下无超过 2 s 的
连续音频停顿；2–16 人房间、100 并发真实媒体会话、24 小时稳定性和资源回收。
同时覆盖突发丢包、150 ms RTT、抖动、带宽骤降、媒体与信令独立中断。

上述是工程目标，不能声称 Go 在当前机器上必然满足。相同硬件、媒体输入、编码、
订阅拓扑及网络损伤下分别测量 Go/C++，报告吞吐、CPU、内存、出口、延迟和质量；
不得以 C++ 语言或“零转码”推断性能更高。现有逐帧组装等待也必须计入延迟。

首批控制面对照命令（Windows 示例，使用专用构建目录避免覆盖运行中的服务）：

```powershell
python tests/go_room_api_parity.py `
  --go-server out/parity-reference/livekit-server-go.exe `
  --cpp-server out/windows-parity/Release/livekit-server.exe
ctest --test-dir out/windows-parity -C Release --output-on-failure
```

Go 参考二进制从上述固定源码执行 `go build -o <output> ./cmd/server` 生成。脚本
随机生成测试密钥和 HTTP 端口，只操作自建进程中的唯一测试房间，清理进程和临时
配置，保留日志、二进制哈希及 `report.json`。返回码 0 表示当前子集通过，1 为
行为差异/断言失败，2 为基础设施错误。SID/时间等非确定字段不做字节相等比较，
对房间 SID 单独检查格式和同一服务内的稳定性；错误比较 HTTP 状态与 Twirp code，
原始错误文本保留在报告中。完整响应字段、错误文本和其他协议仍需后续门禁覆盖。
